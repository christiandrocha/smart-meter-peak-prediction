## What Shipped

Closes PEAK_MODEL F-03 and PEAK_MODEL_CONCURRENCY F-02 (follow-up file
`.claude/sdd/follow-ups/F_PEAK_MODEL_03.md`). The user-run reset
`scripts/reset_peak_model_outputs.py` drops `silver.weather_hourly`,
`ml.household_features_daily` and `ml.household_labels_daily` with `--confirm`. Before the first
DROP, and in the dry run too, it now checks that both peak jobs are idle:

- `smart_meter_peak_model` and `smart_meter_peak_model_training` are found by base name in one
  page of `jobs.list`, with the development prefix stripped. No match, two matches, or a full page
  refuses (ADR 0014).
- The job id and the active runs of each job are read with the shipped `pipeline_guard` rules,
  through a new job-only mode `check_jobs`, appended to `pipeline_guard.py`. The peak and
  pipeline-only modes are byte-equal to v0.7.3.
- The idle set is the two peak jobs. The ingestion job and the pipeline are not in it, because the
  three dropped tables are not read or written by them (RESET_GUARD A-59).
- Every refusal before the first DROP prints one line, `refused, nothing dropped: ...`, and exits 2.
  A failed DROP exits 1. No option or variable skips the idle check.
- The check is the last read before the first DROP. It proves that no run was active at that read,
  not that none starts during the DROP statements (RESET_GUARD F-03).

## Lessons Learned

Drafted by the ship agent from the BUILD_REPORT (findings RESET_GUARD I-01 to I-08 and the
Deviations table), the DESIGN, the DEFINE and the live run record of 2026-11-12. Every row is
drafted and not confirmed by the user; the user was not asked these questions.

| Category | Lesson | Action for future features |
|---|---|---|
| Platform (live gate) | The first live attempt did not run. The runbook and the AC-202 command name the bare `python`, which this machine does not have (only `python3` and `.venv/bin/python` exist). The user's first run used a leading `!` in the shell (bash negation); the shell printed `Command 'python' not found` followed by `exit 0`, so the `!` hid the failure. The run that passed used `.venv/bin/python` with `echo "exit $?"` | Name the project interpreter in every live command (`.venv/bin/python`), and end each live command with `; echo "exit $?"` so that the exit code is printed by the command itself. RESET_GUARD F-01 carries the change to the runbook and the script docstring |
| Build (record and plan, drafted, not confirmed by the user) | The BUILD_REPORT AC-202 row still names the command with `python`, while the record below it shows the command that was run, with `.venv/bin/python`. The row is the plan and the record is the evidence, but the difference is not in the Deviations table | When a live command differs from the one an AC row names, record the command as run and the reason in the Deviations table on the day, as AC66_ZERO_NEW_RUNS asked |
| Spec (scope of a follow-up, drafted, not confirmed by the user) | PEAK_MODEL F-03 named "the ingestion job and the three peak jobs". The bundle deploys two peak jobs, and the three dropped tables are not read or written by the ingestion job or the pipeline (A-59). The DEFINE fixed the idle set to the two peak jobs (D-104, Q-40) | When a follow-up names a set of jobs or tables, check the set against `databricks.yml` and the code that reads or writes the tables before the DEFINE states the requirement |
| Spec (shipped pins, drafted, not confirmed by the user) | The feature changes the version and the reset script, which three shipped tests pin byte by byte. Naming the narrowing (DA-68) in NFR-57 and AC-197 was done by `/iterate` after the DESIGN was drafted (DESIGN change log, 2026-11-12) | When a new feature breaks a shipped pin, name the pins, the allowed narrowing and the count rule in the DEFINE at the first draft, not later |
| Build review (exception hierarchy, drafted, not confirmed by the user) | `StatementFailed` subclasses `ResetRefused`, so a failed count statement printed without its `row counts:` label. The code review found it (RESET_GUARD I-02, fixed in the build). The DESIGN line-shape table named the other error and not the subclass | When an exception class subclasses one the procedure already handles, add a row per subclass to the DESIGN's line-shape table and a test that names it |
| Build (stale bytecode, drafted, not confirmed by the user) | AC-196 failed once from a stale `.pyc`: an edit in the same second with the same size was not recompiled (RESET_GUARD I-03). A fresh checkout is not affected | Clear `__pycache__` in the working tree before the final full `pytest` run of a gate, and keep the rerun result in the BUILD_REPORT |

| Design (external-format assumption, drafted, not confirmed by the user) | The base-name lookup depends on the development-mode name prefix, which no unit test can check. The DEFINE listed it as A-57 with a live AC (AC-202), and the live run confirmed it. The ADR names the revisit condition | Keep every assumption about an external format as an A-NN with a live AC, and write the revisit condition in the ADR, as ADR 0014 does |

## Self-Review

- **Weak points:** The live gate is one dry run in the idle state. The busy and unreadable paths
  rest on fakes (RESET_GUARD F-02). The runbook and the AC-202 text still name the bare `python`
  (RESET_GUARD F-01). `_read_named_job` is a copy of `_read_job` (RESET_GUARD F-04).
- **Risks:** The base-name lookup refuses if the development prefix format changes or a second
  deployment with the same name appears. Every such case refuses, so the cost is a blocked reset,
  not a wrong drop. The race window between the last read and the DROP statements stays open
  (RESET_GUARD F-03).
- **What I would do differently:** Run the live command as the runbook writes it, in a clean shell
  with the project interpreter, before the gate, and record that run in the BUILD_REPORT. Spike the
  bundle summary before the name lookup became the primary source (RESET_GUARD F-05).
- **Next improvement:** Close RESET_GUARD F-01 through the CHANGE track, so that the runbook names the
  project interpreter and a test pins it. Then record the ship PR in the closure PR and cut the tag
  `v0.8.0` (RESET_GUARD F-07).
