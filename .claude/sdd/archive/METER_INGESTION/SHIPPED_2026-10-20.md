## What Shipped

Household-level ingestion of smart-meter readings on Databricks Free Edition. Two sources feed one
Bronze layer: historical half-hourly CSV files landed in a Unity Catalog Volume, and readings after
the study cutoff, published to Aiven for Apache Kafka by a local Docker replay producer. A Lakeflow
pipeline rebuilds Silver and Gold from Bronze. A daily job runs the whole chain. The output is the
input contract of PEAK_MODEL (daily consumption, monthly data quality).

**Delivery state.** The code is not on `main` yet. Four stacked pull requests are open and
unmerged: #1 `feat/meter-ingestion` (PR 1: sampling, producer, environment spikes) <- #2
`feat/meter-ingestion-pr2a` (Bronze, Silver and Gold libraries, local harness) <- #3
`feat/meter-ingestion-pr2b` (notebooks, pipeline wiring, bundle resources) <- #4
`feat/meter-ingestion-pr3` (integration tests, runbook, README). Merge order: #1, then retarget and
merge #2, #3 and #4 in turn.

## Lessons Learned

| Category | Lesson | Action for future features |
|---|---|---|
| Platform (Aiven free tier) | Powering off the free Kafka service empties the topic and resets its offsets. A run after power-on fails under `failOnDataLoss` and leaves an uncommitted offsets batch that fails every later run. Checkpoint resume does not cover a power-off (ADR 0001, DA-11) | Design as if the free broker is ephemeral. Keep the Kafka reset in the runbook (drop the Bronze Kafka table and its checkpoint, re-produce). Do not assume offsets survive a power-off |
| Platform (serverless jobs) | `ingest_kafka` ran twice per job run although the task set `max_retries: 0`, for an `INTERNAL_ERROR` and a `FAILED` attempt. The cause is not verified; a serverless automatic retry is the likely one (ADR 0001, DA-12) | Verify the retry behaviour before relying on single-attempt semantics. Tests that depend on attempt counts must count attempts (follow-up F-02) |
| Platform (Volumes) | `databricks fs rm -r` left a checkpoint folder in place, twice | Delete checkpoints in Catalog Explorer, one subfolder at a time, and confirm with `databricks fs ls` (runbook, "Bronze reset") |
| Delivery (biggest delay) | The replay that published nothing slowed the feature most. Its output was not kept and the topic was not checked, so the job ran on an empty topic, step C failed with Bronze Kafka at 0 rows, and the diagnosis took a topic watermark check, a 10-event producer probe and a cleanup of the probe events (the topic had to be recreated, because `delete_records` hung on the Aiven free tier, plus a Bronze and checkpoint reset) | Treat a replay as done only when it is verified: keep the producer log (its last line is `published N event(s)`), and check that the topic watermarks add up to the manifest `stream_rows` before running the job. Add that check to the runbook produce step, as a small script that prints watermarks and no credential. Probe a new environment with `--limit` and recreate the topic, instead of deleting records, to remove probe events |
| Platform (SQL warehouse) | One statement stayed PENDING for more than 900 s and timed out the SQL test fixture | Set an explicit statement timeout in the fixture and report the statement state when a query stays pending |
| Platform (capacity) | An update failed with RESOURCE_EXHAUSTED between the `before` snapshot and the update of the I-18 pair, which invalidated the pair | Run a before/after pair back to back with no other update in between. When the window is broken, drop the objects and re-run the pair from the same empty state |
| Spec (Aiven free tier) | The spec did not account for how the Aiven free tier behaves. DEFINE and DESIGN assumed the topic survives an outage and the stream resumes at the checkpoint (AC-10 recovery, runbook "Broker outage"); the spikes tested an unreachable broker (DA-05) but not a power-off and power-on, idle shutdown, retention or topic admin calls. The build found that a power-off empties the topic and resets offsets (DA-11), that `delete_records` hangs, and that every outage test therefore costs a Kafka reset and a full replay | Before DESIGN, spike the free-tier lifecycle of every managed service the feature depends on (power-off and on, idle shutdown, retention, admin operations) and record each result as an assumption in the runtime ADR; write AC recovery clauses against the observed behaviour, not the general Kafka semantics |
| Spec (event log) | Spike 04 showed that an update with no new input writes no expectation metrics. Per-update rule counts were therefore not observable (ADR 0004, DA-01) | Spike how a metric is observed before writing per-run wording. Here the counts became table totals over a published evaluation table |
| Spec (failure classes) | The seed-42 stream has no invalid message, so the replay rule for dropped rows was not exercised by real data. The gap was found in review (I-15, I-22) and fixed by keying dropped rows on their business key (ADR 0005 amendment) | An acceptance criterion that names a failure class needs a fixture or test for that class at DEFINE time |
| Spec (given clauses) | AC-17 described a cross-source duplicate that the cutoff rule (QR-06) makes impossible (I-21) | Check every Given clause against the rules that admit rows, at DEFINE |
| Spec (shared workspace) | AC-26 "exactly one pipeline in the workspace" conflicts with an unrelated pipeline in the shared workspace (I-10) | Scope workspace-level assertions to resources the bundle owns, by name |
| Tests (Jobs API) | The SDK page limit (26) and partial `only=` runs, which list every task (skipped tasks end `DISABLED`), made the run-selection fixture count wrong runs | Unit-test run-selection fixtures against recorded SDK responses before the first live run |
| Tooling (spec gate) | `scripts/check_specs.py` matched "fail" in test names and reported a false positive | Fixed in eb935de. Gate patterns match result cells, not free text |

## Decisions to Carry Forward

| ADR / decision | Why it matters for later features |
|---|---|
| 0001 Runtime environment constraints | Free Edition limits (serverless only, at most 5 concurrent job tasks, one active pipeline per type, daily quota, restricted outbound network) and the Aiven free-tier behaviour (short retention, power-off empties the topic). Every later feature on this stack starts from these limits. Change Log records DA-11 and DA-12 |
| 0002 Aiven Kafka with SASL_SSL SCRAM and a secret scope | The only accepted way to authenticate to Kafka from serverless. Credentials never appear in code, configuration or logs (AC-29 verified live). Producers and consumers reuse the same scope pattern |
| 0003 Catalog `smart_meter_dev` created by an idempotent setup task | Catalog and schema names are fixed by the contracts and PEAK_MODEL. Bundle development mode would prefix schema names, so the setup task (not the bundle) creates the catalog and the `ml` schema. Production is a variable override only |
| 0004 One Lakeflow pipeline with quarantine routing | Silver and Gold are rebuilt by one triggered pipeline. Rule counts are table totals over the current evaluation state, not per-update deltas. Future rules are added in `rules.py` and must keep this definition |
| 0005 First-ingested-wins deduplication | The winner of a key is the earliest `_ingested_at`, then the smallest `_source_ref`. This makes re-runs and full refreshes produce the same Silver and Gold rows (AC-17, AC-27). Dropped rows use the same rule on their `_dedup_key` |
| 0006 Bronze tables, not Kafka, are the replay source | Silver and Gold are rebuilt from Bronze, including with the Kafka service off (AC-27). Any reprocessing plan starts from Bronze and its checkpoint, not from topic retention |
| Data contracts in `docs/contracts/` | PEAK_MODEL consumes `gold_household_daily_consumption`, `gold_household_data_quality_monthly`, `gold_household_data_quality` and `silver_households`. Changes to these go through `/iterate` on the feature that owns them |

## Self-Review

- **Weak points:** 10 of 35 ACs have only local evidence. Live evidence covers one seed-42 dataset and one Free Edition workspace. AC-28 is `Partial`, so the first deploy on a fresh workspace has not been shown. AC-29 checks sentinels only. The serverless retry behaviour behind the double `ingest_kafka` attempt is not explained.
- **Risks:** Nothing is on `main`, so the feature exists only on four stacked branches. The live runs depend on a free Aiven broker that powers off after inactivity; a power-off resets the topic and needs a Kafka reset before the next run. The duplicate `ingest_kafka` attempts are not explained, so any retry-sensitive logic rests on the idempotent Bronze write (AC-08) rather than on single-attempt execution.
- **Trade-offs:** Silver and Gold are materialized views recomputed over Bronze (ADR 0004, 0005). This keeps the rebuild rule simple and proven by AC-27, but the recompute cost grows with the history. The seed-42 run took about 3 minutes in the pipeline stage, far inside the budget; the margin at full scale is not measured. Rule counts are table totals, so they are cheap to define but cannot show per-run change.
- **Next step:** Merge PRs #1 to #4. Then run F-01 and F-02 (fresh-workspace deploy and retry check) before the first release tag, and take F-03 to F-08 through `/iterate` or the next contract change.
