## What Shipped

The daily ingestion job `smart_meter_ingestion` now has a read-only pre-check of the shared pipeline.
The task `check_silver_gold_idle` runs after the two ingest tasks and before `refresh_silver_gold`.
When an update of `smart_meter_silver_gold` is in progress, or the pipeline state cannot be read,
the task fails at once. Its message names the blocking update and the action to take. The task has
no retries and does not write. Bronze ingestion is never blocked: the check runs after
`ingest_files` and `ingest_kafka`. The task `ingest_kafka` now sets `disable_auto_optimization: true`
with `max_retries: 0`, so a failed Kafka read runs exactly once and the next daily run is the retry
(AC-95). The check uses a pipeline-only mode that was appended to `pipeline_guard`. The peak mode is
unchanged: the diff against `v0.3.0` has only added lines. The decision is in ADR 0013; the dated
notes of ADR 0012 and ADR 0008 (2026-10-23) record the coexistence with the peak job. The reverse
check closes PEAK_MODEL_CONCURRENCY follow-up F-01.

The ingestion job has five tasks and at most two run at once (AC-28). The check is the only task on
serverless environment version 2 (`ingestion_check_env`, AC-83). The job holds no reference to the
peak job, because a reference in both directions forms a bundle cycle (A-30, ADR 0013). The daily
schedule of both jobs and the pipeline definition are unchanged.

## Lessons Learned

What slowed the feature down (answered by the user at ship): the user confirmed lesson 1 below. The
other lessons are the ship agent's reading of the build report and the spike. They are marked
*drafted, not confirmed by the user*.

| Category | Lesson | Action for future features |
|---|---|---|
| Live testing (confirmed by the user) | The free Aiven service powers off after 24 h without traffic, and that empties the Kafka topic. The live block was split across days, so the Kafka-on tests needed a second Kafka reset and a replay on 2026-11-04 (247,569 events). The Aiven state was also not probed before the sequence | Run the Kafka-on live block in one sitting. Before resuming on another day, probe the topic count and redo the Kafka reset if it is empty (build I-09). Plan the run order (AC-95 last, with Aiven off) in the runbook before the first live run |
| Platform (validation, drafted, not confirmed by the user) | Spike 07 showed that `bundle validate` passes while `bundle deploy` fails with `Error: Cycle` when two jobs reference each other (A-30). Validate does not catch a Terraform cycle. The spike also showed that `disable_auto_optimization` does not stick on a pipeline task (A-25 invalidated, D-51). Both facts changed the design after the spike was accepted | List the deploy as the probe for every bundle reference in the spike, not only validate. Test the readback of each setting on each task type (notebook and pipeline) in the spike, not only that deploy accepts it. Guard G-27 (no job reference in the ingestion file) turns the cycle into a unit test |
| Spec (assumption with a fallback, drafted, not confirmed by the user) | A-25 (`disable_auto_optimization` on a pipeline task) was an assumption in the BRAINSTORM with an Out-of-Scope fallback. ## Decisions to Carry Forward

| ADR / decision | Why it matters for later features |
|---|---|
| 0013 Read-only, pipeline-only pre-check in the ingestion job; no platform retry of `ingest_kafka` | Any later job that starts an update of a shared pipeline uses a pre-check of the same kind. The pipeline-only mode in `pipeline_guard` is the shared entry point. No job may reference another job in this bundle in both directions (cycle, A-30) |
| 0012 dated note (2026-10-23) | Both daily jobs check the pipeline before their own pipeline task. The revisit trigger of ADR 0012 (a reverse check) is answered by ADR 0013. The races remain (see Follow-ups) |
| 0008 dated note (2026-10-23) | The ingestion job checks the pipeline before its own refresh. The overlap rule is enforced by pre-checks in both jobs |
| Fail closed in both jobs | An API or SDK fault now blocks the Silver and Gold refresh of both jobs until it is fixed. Bronze is kept. This is the cost to watch in the first scheduled runs (follow-up F-03) |
| Auto-optimization on notebook tasks only (DA-29) | `disable_auto_optimization` with `max_retries: 0` gives one attempt on a notebook task. On a pipeline task the field does not stick (A-25). Pipeline tasks cannot be protected this way |
| Environment version 2 only on the check (AC-83, DA-28) | The check's environment (`ingestion_check_env`) is separate. The other tasks keep the default environment, so a change to environment 2 affects one task |
| Pins (AC-84, AC-85, AC-92) | The ingestion job is pinned to tag `v0.4.0` after the tag is cut. The `v0.1.0` fixture is byte-exact. The shipped guard tests and the peak module are pinned to `v0.3.0`. Any change to these files is a new feature or `/iterate` |
| Aiven free service (ADR 0002, build I-09) | The free plan powers off after 24 h without traffic and empties the topic. Kafka-on live tests need the topic probe before each session |

## Self-Review

- **Weak points:** The live evidence is two sessions 12 days apart with a Kafka reset in between, on the same build and the same replayed sample. AC-97 relies on one timing observation on dev (DA-31). AC-98 reads evidence written by a shipped test and needs Aiven on. The additions-only check of AC-92 cannot run without the `v0.3.0` tag, and the tagged legs of AC-84 and AC-85 need `v0.4.0` after F-01.
- **Risks:** Fail-closed now applies to both jobs, so an API or SDK change costs both refreshes until it is fixed (F-03). The race window remains in both directions (F-04). The first scheduled runs are the first unattended test of the check.
- **Trade-offs:** A pipeline-only check avoids the bundle cycle and the mutual refusal, at the price of not naming the peak run and not covering a peak run's later tasks (A-28). Placing the check after the ingest tasks keeps Bronze ingestion when the pipeline is busy, but the check never runs when `ingest_kafka` fails (AC-95 asserts this as intended). Explicit pins (FR-51) make each change of these files a deliberate act, at the cost of one more pin to move per feature.
- **Next step:** Open the ship pull request on `ship/ingestion-guard` (stacked on PR #29, retarget to `main` after #27 to #29 merge), merge in order, tag `v0.4.0` (F-01), and watch the first scheduled runs (F-03). Then decide F-10 as a new feature cycle.
