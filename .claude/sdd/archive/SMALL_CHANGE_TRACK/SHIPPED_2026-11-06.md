## What Shipped

`scripts/check_specs.py` gains a CHANGE phase for one-document changes that meet the eligibility
criteria E1 to E8. A CHANGE document `CHANGE_<FEATURE>.md` replaces the DEFINE, DESIGN,
BUILD_REPORT and SHIPPED documents of an eligible change. The checker validates:

- the Eligibility rows: exactly one row per criterion, result `Yes` (E8 may also be `Relaxing`,
  which needs a `## Rule Changes` section with the before and after quotes, a `gh api` block and
  `User OK:`), and a non-empty evidence cell;
- the traceability from Acceptance Criteria to Test Strategy and, when `Complete`, to Evidence,
  with no failing row and an `Evidence commit` SHA.

The checker also reports every `.md` file in `features/` or `reports/` whose name has no phase
prefix as an error; before, such a file was skipped silently. Each phase has an explicit final
status in a literal map. In the archive, a folder with a CHANGE document holds only that document,
in status `Complete`, and no SHIPPED document. Rules (b) and (c) of SPEC_ARCHIVE_GATES read
archived CHANGE documents.

Entry points: `scripts/check_specs.py` (`check_change`, `FINAL_STATUS`, `load_docs`),
`.claude/sdd/templates/CHANGE_TEMPLATE.md`, `tests/test_check_specs.py` (AC-120 to AC-131),
`.claude/sdd/README.md`, `docs/conventions/git.md` (branch names `change/`, `spec/`, `build/`,
`ship/`) and the "How work is done here" section of `CLAUDE.md`. No production file changed.

Build branch head 3a3b868; the code evidence is on commit 4668af3 (BUILD_REPORT Verification Log),
which also closes SMALL_CHANGE_TRACK I-03 and I-08 on the user's decision of 2026-11-06.

## Lessons Learned

All drafted from the BUILD_REPORT evidence on 2026-11-06. Drafted, not confirmed by the user.

| Category | Lesson | Action for future features |
|---|---|---|
| Spec (test cases) | The DEFINE gave one valid and one invalid case per rule. Review after the build still found three Medium gaps: a fenced `## Rule Changes` example hid the real section, an AC-less CHANGE document passed, and `Not run` passed a `Complete` document (SMALL_CHANGE_TRACK I-01 to I-03). | For each new checker rule, list the adversarial forms in the DEFINE test table: fenced examples, empty tables, and every result value that is not the expected one. |
| Design (regex and text) | DESIGN G-41 gave three capture groups; the template has four columns. The build changed the regex and recorded it as mechanical, so the DESIGN text stayed stale (SMALL_CHANGE_TRACK I-09). | When the build changes a regex or a column count, update the DESIGN through `/iterate` in the same change. A mechanical deviation still leaves stale text. |
| Build (evidence) | The full `pytest` run (643 passed) was made before the review-fix commit 0e56f72. The Verification Log therefore mixes commits: the full run predates the last code commit, and the report head is 046413c. | Run the full suite on the final code head before the BUILD_REPORT is `Complete`, and name that SHA on every row of the Verification Log. |
| Build (template) | The CHANGE template needed its `## Rule Changes` part inside a fenced example, because a real heading broke the heading-equality test. The conflict between an optional section and the heading check was found only in review. | Name such template conflicts in the DESIGN before the build, and prototype the template against the checker first. |
| Process (scope) | `docs/conventions/naming.md:42` still shows the `feat/` branch prefix (SMALL_CHANGE_TRACK I-08). The file was outside the manifest, and no repository-wide search for the renamed convention was part of the scope. | At the DEFINE scope step, search the repository for the old value of each renamed convention, and list each hit as in scope or out of scope. |

## Self-Review

- **Weak points:** Rule (b) will warn on four `Open` rows of the archived BUILD_REPORT (I-05 to
  I-07, I-09) until the follow-ups close; the BUILD_REPORT is not edited, so the warnings stay. E1
  to E8 and D-91 are declared, not checked against history (F-01).
- **Risks:** A `Deferred: <reason>` row lets a CHANGE document reach `Complete` without that
  evidence; it is only listed as a warning, so reviewers must read the warnings. The ship PR stacks on the build PR, so the merge order matters: spec, then build, then ship, with
  the ship PR's base moved to main once the build PR has merged. The unrecognized-name error turns
  any stray note in `features/` into a failing check.
- **What I would do differently:** Write the adversarial test cases into the DEFINE, and run the full
  suite on the final code head before the BUILD_REPORT is `Complete`.
- **Next improvement:** Run `/iterate SMALL_CHANGE_TRACK` for F-09 after the merge, then use the CHANGE track on the first small
  change, which settles whether F-01 is worth its cost.
