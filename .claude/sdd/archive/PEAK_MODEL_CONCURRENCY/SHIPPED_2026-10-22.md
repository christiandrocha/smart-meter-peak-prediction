## What Shipped

The daily job `smart_meter_peak_model` now starts with a read-only pre-check. Before the shared
pipeline task `refresh_silver_gold` runs, the task `check_pipeline_idle` reads the state of the
ingestion job `smart_meter_ingestion` and of the pipeline `smart_meter_silver_gold`. When an
ingestion run is active, or the pipeline has an update in progress, the task fails at once and
its message names the blocking run or update. When the state cannot be read, the task fails
closed. The task has no retries and does not write. The decision logic is the SDK-free library
module `pipeline_guard`, which the integration runner reuses. Decisions are in ADR 0012 and the
dated note of ADR 0008. The daily job's schedule, concurrency limit and the ingestion and training
definitions are unchanged (AC-68, AC-78).

## Lessons Learned

What slowed the feature down (answered by the user at ship): "All three point to the same upstream
intervention: tighter spike scope before /design, specifically checking platform API surfaces and
error states rather than just feasibility."

1. The mid-build design change: the pipeline's overall state (`pipelines.get(...).state`, G-21, U-05)
   was found only in code review. The design decided busy from `latest_updates` alone.
2. The spike 06 surprise: `databricks-sdk` 0.40.0 in serverless environment version 2 has no
   `WorkspaceClient` timeout keywords. The timeouts are `Config` fields. Spike 06 was rerun and the
   change went through `/iterate`.
3. Live-test overhead: serverless runs take about 9 minutes, AC-74 needed the Aiven Kafka service
   on, and the CLI refresh token expired mid-run. AC-75 and the deployment test had to run again
   after re-authentication.

The user answered question 1 only; the three slowdowns above are that answer. The spec gaps and the
workflow friction below are the ship agent's reading of the build report. They are marked *drafted*
and are not yet confirmed by the user.

| Category | Lesson | Action for future features |
|---|---|---|
| Platform (API surface, answer to Q1) | The spike checked feasibility (the calls work) but not the signatures on the runtime SDK. `WorkspaceClient` in 0.40.0 rejects the timeout keywords the design named (DA-20, G-20) | Run the platform spike before `/design`. Probe API surfaces and error states on the actual runtime SDK version: signatures, field formats, enum sets, and refusal and error states. Not only feasibility |
| Platform (state model, answer to Q1) | The pipeline's overall state (`pipelines.get(...).state`) can read busy when `latest_updates` lists no active update. The design did not name it (G-21, U-05) | In the spike, read every state field the decision uses, and list the enum values seen (DA-22 and DA-26 in this feature) |
| Live testing (answer to Q1) | A serverless run takes about 9 minutes. AC-74 needs the Aiven Kafka service on. The CLI refresh token expired during a live sequence and two tests had to run again | *Drafted:* before a live sequence, check the CLI session and the Aiven service, and plan about 9 minutes per serverless run |
| Spec (pipeline state, drafted) | The DESIGN named only `latest_updates` for busy. Overall pipeline state needed its own rule and its own tests | Name every state field a decision reads, with its allowed values, in the DESIGN |
| Platform (SDK timeouts, drafted) | The DESIGN assumed the timeout keywords on `WorkspaceClient`. They are `Config` fields | Pin the client construction in the DESIGN to the runtime SDK version (corrected by spike 06, DESIGN change log 2026-10-22) |
| Platform (timestamp format, drafted) | `creation_time` arrives as ISO 8601 with a `Z` suffix, not as epoch milliseconds only | Record the observed format in the spike, and test both forms when a parser accepts either |
| Build (shipped tests, drafted) | Adding a task to the daily job broke shipped PEAK_MODEL tests (exact task lists, integration layout). The manifest listed only part of them | When a change adds or removes a task, grep the shipped tests for the exact task lists and list every file in the manifest (entry 18b was added late) |

## Decisions to Carry Forward

| ADR / decision | Why it matters for later features |
|---|---|
| 0012 Read-only pre-check before the shared pipeline task, failing fast and closed | Any job that starts an update of a shared pipeline uses a pre-check of the same kind. The decision logic is `pipeline_guard`; its states come from the SDK enums (AC-69) |
| 0008 dated note (2026-10-22) | The daily graph starts with the pre-check. The overlap rule is now enforced by the pre-check task, not by the schedule alone |
| Platform rules applied in code | Serverless environment version 2 with `databricks-sdk` 0.40.0 is the runtime. Client limits are `Config` fields. The pre-check task has `max_retries: 0` and `disable_auto_optimization: true` |
| Bundle references (DA-19) | A bundle reference reads another job's id and the pipeline id at deploy time. It passed at the first deploy and is the way to point at the ingestion job |
| AC-78 pins | The ingestion job and the pipeline are pinned to tag `v0.1.0`; the training job is pinned to tag `v0.2.0`. A change to any of them is a change of a shipped definition and needs `/iterate` or a new feature |

## Self-Review

- **Weak points:** AC-75 depends on the timing of a no-op update. The busy cases are live only on one workspace. The decision is verified against the SDK 0.40.0 surface only through spike 06 and the live runs, not through a runtime-version test in CI.
- **Risks:** The pre-check fails closed, so an API problem costs a daily run (F-04). The race window between the check and the pipeline start is accepted (F-03). The reverse overlap, an ingestion run started during a peak run, is still unguarded (F-01).
- **Trade-offs:** A fail-fast pre-check adds a task and about 18 to 32 s (measured) to each daily run in exchange for a named message. Fail-closed reads an unreadable state as busy, so a run can be lost to an API fault. The guard is SDK-free and unit-tested against a recording fake, so the fake must follow the SDK enums (AC-69).
- **Next step:** Open the ship pull request, merge it, and cut the tag `v0.3.0`. Then decide F-01 as a new feature cycle, and watch the first scheduled run for F-03 and F-04.
